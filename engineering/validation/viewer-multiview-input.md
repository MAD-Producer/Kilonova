# #221：逐视角编辑几何与拾取查询

本阶段消除下一步多视图输入接入的全局视角依赖。没有开启产品布局入口，
没有把查询接口当作已完成每格手势或 UI 验收。证据见
[清单](viewer-multiview-input-evidence/manifest.json)。

## 实现

`Session::snapshot_for_view` 复用普通 snapshot 的同一投影实现，显式提供
`Scene::fork_view` 的相机，不临时替换共享 scene/observer。选框、原始源平面、
矢量路径和蒙版的矩阵均使用该视角。普通 `snapshot()` 继续传原 scene 和 observer。
显式视角不会冒用共享 observer 的撤销可用标记；其导航历史由后续视图所有者负责。

`Session::hit_candidates_for_view` 复用原效果输出拾取边界和前后顺序，
只改变查询所用的已采样视角。原 `hit_candidates` 的采样、坐标和回复格式保留。
这些查询不修改工程、时钟、全局相机或项目撤销栈。

桌面 worker 接入拥有相机数据的 `ViewerInput` 请求：

- `States` 一次只接受 1/2/4 个视角，全部成功后才返回完整数组。
- `Pick` 使用该请求显式携带的相机与合成像素坐标。
- 请求捕获原有 `KeyframeSource` 和精确 frame。来源/时钟失效、浮窗已关闭是
  正常取消，返回 `cancelled` 和原因，且在解析相机前取消。
- 相机不存在、格数非法或坐标非法保留真实 cause；逐格状态错误另含格索引和阶段。
- 只读查询不主动清理原呈现 stamp。新增操作名沿原 worker 的在途状态、Info start、
  完成计时、panic 回复和默认错误信道处理；没有新增日志器、计数器或恢复重试。

当前没有每帧查询的产品调用者，不宣称已证明新增 UI 调用频率、帧预算或零延迟。
界面接入时仍须限制在途查询，校验回复的视角/来源身份，不能把旧回复覆盖新活动格。

## 验证与失败记录

本轮宿主完整 lib 测试 113 项通过，另有桌面 5 项不同验收通过：新增 worker 查询 1 项、
原生多视图呈现/检查 2 项、四精度截图 1 项、显式执行的旧单视图快照 1 项。
合计 118 项，0 失败、0 忽略。恢复重跑、首次失败和负对照不重复计数。
Windows FFmpeg 测试/开发版编译及样式消费者检查结果列于清单，保留全部告警。

新宿主用例使用两台相反方向相机、空间平面、矢量路径和蒙版：

1. 每视角的选框与 renderer 的该相机 fork 多边形一致，原始源矩阵与同一视角的
   世界矩阵一致。两台相机的四类几何均不同，侧视 observer 的几何也不同。
2. 同一点从两台相机分别拾取到真实前景对象 7 和 8。
3. 成功和失败查询前后的完整共享 snapshot 严格相等。缺失相机、非相机对象和
   非有限坐标拒绝，不改任何共享状态。
4. 对象 7 的一次实际编辑同时反映到两个视角，对象 8 的源矩阵不变；真实 undo
   恢复两个视角的选框、源矩阵、蒙版和矢量几何。

新增桌面用例使用实际 Engine worker，但不创建原生窗口或 GPU surface。
验证真实状态/拾取回复、默认文件与 Error stderr、stdout 隔离、两个操作名的
Info start，以及过期 frame、缺失来源身份和已关闭窗口取消后恢复查询。
原生 surface、快照和显示编码由本轮另行执行的四项既有验收覆盖；不声称这些
既有验收已验证新查询与可见多视图控件之间的完整交互。

首个宿主用例误把已有 HitCandidate 的 `id` 字段写成 `object`。源码改正后，
首次执行仍调用了改正前编译的程序，出现 Null 与 7 的断言失败；重编译后通过。
保留 `build-host-first.log` 和 `host-first.log`。该旧程序未保存独立副本，
不声称已完整保留其程序身份；生产回复 schema 和值没有改动，既有断言也没有放宽。

运行时负对照只把 worker 的拾取相机强制改成合成相机，保留状态查询和所有断言。
编译成功后，用例实际拾取到对象 8，因预期对象 7 而退出 101。
finally 逐字节恢复源码，SHA-256 与程序身份见 `negative-receipt.json`；
恢复后的原正向程序再次通过。此负对照验证实际对象错误，不以编译失败代替拒绝证据。
