# 工程保存中断与临时文件恢复

Refs #132、#135。只补测试，不修改正式构建的保存算法、错误信道或工程格式。

## 实际执行路径

新用例调用实际 `storage::save`、文件写入、文件同步、平台替换、目录发布与 `storage::load`，不用成功返回的文件系统 mock。在实际保存路径添加五个 `cfg(test)` 检查点；只在新用例的子进程所属线程设置目标阶段。其他测试不启用中断；正式构建不含检查点、线程局部状态或环境变量读取。

子进程在目标阶段调用 `process::exit(86)`，跳过 Rust 栈析构；父进程要求精确退出码，核对目标字节及完整加载结果，并检查临时文件是否仍存在。不是通过 panic/unwind 触发清理后再声称“崩溃后没有残留”。子进程输出有单独收集，30 秒为新增测试的期限，不改变产品超时或原有用例；无法完成时保留原等待失败与终止结果。

| 检查点 | `project.json` | 临时文件 |
| --- | --- | --- |
| 创建临时文件后 | 完整旧字节/旧模型 | 仍在，空文件 |
| 写入后、文件同步前 | 完整旧字节/旧模型 | 仍在，完整新字节 |
| 文件同步后、发布前 | 完整旧字节/旧模型 | 仍在，完整新字节 |
| 平台替换后 | 完整新字节/新模型 | 已由替换消费 |
| 发布确认返回后 | 完整新字节/新模型 | 已由替换消费 |

随后由调用者明确发起一次正常保存，验证残留临时文件被正确覆盖、最终完整新工程可重新加载且临时文件消失。不自动重试中断的保存，也不重启产品 worker。五个场景属于一个测试，不计为五个缺陷或五条独立测试。

## 信号与边界

| 项目 | 分类与处置 |
| --- | --- |
| S1：进程中断 | 新覆盖：实际保存的五个阶段，旧/新字节身份、完整模型、临时文件和显式后续保存 |
| S2：破坏性写入 | 受控对照把中断子进程的临时路径改成目标路径；应因旧工程被截断而失败。只是证明用例能检出这类缺陷，不声称当前产品存在此缺陷 |
| S3：原生错误/日志 | 生产无新增故障路径或日志点；现有 `storage_publication.rs` 对 publish 原生原因、published 标志、Windows sharing violation 与显式恢复的覆盖保持，不把它计为本批新增观察 |
| S4：平台区别 | Unix 的“替换后”在目录同步之前；Windows 已使用 write-through 替换，所以最后两个检查点不是两个不同的硬件同步保证 |
| S5：真实掉电 | 未覆盖：`process::exit` 不清空操作系统缓存，不能证明断电后的介质状态，也不能检出所有漏调 fsync 的实现。保留 #132 原始“断电模拟”验收为未完成，不用进程退出代替真实存储故障模型或虚拟机掉电测试 |
| S6：其他范围 | 不覆盖资产文件/祖先目录的持久性、文件系统或设备违反刷盘保证、写入系统调用内部的部分写入、目录同步失败注入、并发保存或网络文件系统 |
| S7：部分临时文件 | 同分支新增第二个实际用例，分别手工留下空文件、半截 JSON、非法 UTF-8 和较长尾部垃圾。重新加载必须读取完整正式工程，下一次显式保存必须完全替换残留；不将手工残留称为系统调用内部故障注入 |

[Rust exit 的说明](https://doc.rust-lang.org/std/process/fn.exit.html)明确它跳过 Rust 析构，但仍可能执行平台/C exit handler；本批不称其为 SIGKILL 或 TerminateProcess。[Unix fsync 说明](https://man7.org/linux/man-pages/man2/fsync.2.html)区分文件数据与目录项同步；[Windows MoveFileExW 说明](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)说明 write-through 标志。正式实现保持原有行为，本次测试不扩大这些系统保证。
