# 效果依赖检查的连续存储

关联 #126；本项不关闭整个预览分配 issue。开始前已核对开放 PR 和本地分支：相机/抠像整合、跟踪和后台预渲染由其他分支推进，本分支只处理效果准备阶段的依赖检查。

## 问题与改动

`PreparationPlan::check_dependencies` 原先为每个效果节点的输入、每个生产者的消费者分别建立 `Vec`，再用 `BTreeSet` 保存就绪节点。一个合法的长效果链即使没有任何循环，每次检查也会重复分配这些小对象。

每个效果节点最多有两个不同输入：同层前一个操作和一个显式图片输入。新实现将两个输入内联保存，消费者使用连续边表与每个节点的表头，就绪队列改用连续工作列表。只计算剩余未消除的图，不输出遍历顺序；因此就绪节点的访问顺序不构成渲染语义。循环诊断仍从同一剩余节点开始，按原有输入顺序找实际循环，保留 typed cause、来源、长度上限和排除下游尾部的行为。

这些都是函数内临时存储，受既有场景与操作数限制；没有跨帧历史，也没有增加 GPU 资源、缓存、预算或回收规则。容量按实际有效输出操作计数，禁用、无输出和准备失败的候选不会扩大操作容量。普通图片链和原始来源仍走原来的不构图快速路径。

## 验证范围

- 新分配测试直接调用真实依赖检查，System 分配器在调用线程计数，夹具与效果准备在计数外。2、8、64、128 层合法效果链各执行四次。旧实现分别为 15、40、276、544 次；改动后均为 8 次。这里固定的是分配次数，临时字节量仍随图规模增长。
- 独立的引用链巡游作为循环判断参考，穷举四层每层“无引用/引用任一层”的 625 种组合；检查实际准备入口返回的 typed cycle、成功和恢复，保留普通链零分配断言。
- 另外检查同一生产者的重复引用、多效果堆叠后实际最终生产者、禁用/零不透明度/准备失败的候选及修复后恢复；准备失败的原始候选错误必须仍被保留。
- 完整预览帧报告增加真实置换效果链，持续修改工程中的参数及变换，每帧要求计划确实重建；按阶段统计实际采样、编码、提交和轮询，并读回完整图片，与独立 Renderer 的输出比较。原有纯色、矢量和遮罩场景及严格断言保留。
- 最终完整渲染库 314 项与六组相关集成测试 24 项全部通过，合计 338 项，0 失败/忽略/过滤。两项生产负对照均按预期失败，FFmpeg 桌面全部 target 的编译检查通过。

## 错误处理与边界

| 项目 | 处理 | 证据与限制 |
| --- | --- | --- |
| DEP-01 正常依赖检查 | 功能优化 | 内联输入、连续消费者和就绪列表；不新增日志站点。 |
| DEP-02 实际循环 | 保留原有错误边界 | 625 种引用组合通过真实准备入口验证，原有循环先于矢量栅格失败、排除下游尾部和恢复的断言保持。 |
| DEP-03 正常快速路径 | 保留正常分支 | 无效果阶段依赖时不构图，不把正常空输入记为错误。 |
| DEP-04 无效候选和零不透明度 | 保留原有功能 | 不把准备失败或没有输出的候选加入循环图；不新增重试、吞错或返回值转换。 |
| DEP-05 错误输出信道 | 既有覆盖 | 错误类型、上下文构造和上层日志入口未改；本次库测试中的输出不冒充默认桌面文件日志/stderr 端到端验收。 |
| DEP-06 完整帧分配 | 尚未完成 | 新测量包含调用线程中的原生后端开销；不计后台线程分配。局部检查的固定次数不等于完整帧固定次数。 |

没有修改 UI、样式 token、命中范围、菜单、依赖或第三方资产。实际 GPU 图片验证也不代表原生桌面连续播放或主窗口截图。带遮罩的每目标渲染通道、其他效果准备/语义图容器和后端编码/提交的剩余分配仍需后续优化；#126 的整体分配与预算验收保持开放。

## 原始失败

最初新增测试使用了 256 层，超过工程既有 128 层上限，失败为夹具的 `layer limit exceeded`。夹具改为既有 `MAX_LAYERS`，保留两条性能断言；随后旧实现按预期在固定次数断言失败。首次改动编译还发现子模块通过父模块导入 `BTreeSet`，恢复共享导入后继续验证。这些失败均保留，不修改既有生产限制或断言来通过测试。

恢复旧的嵌套存储后，最终三条新增测试中的性能测试按预期失败（另外两条语义测试通过）；故意丢弃显式图片依赖边后，两条语义测试失败，性能测试仍通过。两项负对照均使用最终新增测试源码，既有断言未改。

恢复第二项负对照时，Windows `Copy-Item` 保留了较早的正式源码时间戳。Cargo 编译了正常 library，却复用了时间更新的负对照单元测试程序，使首次最终库运行出现 310 通过、4 失败。原始输出和源码/程序身份、时间戳已保存为 `restored-timestamp-render` 与 `restored-timestamp-evidence.json`。正式源码 SHA-256 与备份一致；随后只更新文件时间戳、重新编译并核对测试程序身份变化，不修改生产逻辑、断言或错误返回来掩盖这次失败。最终验收必须取重新编译后的完整运行，不能使用此前仅准备了两个新测试的 313 项成功记录替代。
