# macOS 字体故障夹具边界修正

#607 的 8e9f238e 在运行 41954252678 / job 127008149834 中，UI 库为 113 通过、两项失败。Rust/GPU 与 Linux 桌面任务已通过，Windows 当时仍在运行；这些结果不代表新提交完成跨平台验证。

原始 macOS 日志确认两种不同前提问题：

1. `shaped_draw_failures_keep_bounded_default_level_causes_and_owner_scope` 用 U+10FFFF 作为必然缺字探针。`supports` 的主字体/固定回退查询为 false，但实际布局还会查系统字体，macOS LastResort 可以返回占位字形，因此“绘制结果为空”的断言失败。现在只在这个缺字故障夹具中关闭系统发现，先断言实际布局确有一个 ID 0 缺字，生产字体发现不变；主/固定回退和正常文本仍按原路径执行。原空结果、六类日志、第 60 次阈值、抑制、图集替换、隐私和 stdout/stderr 断言全部保留。
2. `source_failures_keep_default_file_stderr_evidence_without_text_or_reopening` 的容量阶段曾遍历全部系统字体。macOS 的 GB18030 Bitmap 解析失败产生一条真实 source Warn，容量拒绝仍按预期产生 Warn/Error，因此文件实际九条，原断言要求八条。现在容量夹具仅装入一张真实可解析且覆盖 A 的已安装字体，独立控制容量边界。原缺文件、原始原因、解析失败、八条文件记录和四条 Error stderr 的断言保持；生产代码不丢弃这条额外 source 故障。

新增容量正负对照：相同真实字体在正常预算下必须成功加载；一个有效字体的拒绝只有一个失败候选，加入空字节无效候选后必须真实记录两个失败候选，仍返回容量错误且不保留字体。它证明夹具隔离，而不是把混合的真实源错误从计数中滤掉。

最终两个目标分别六项、四项通过，零失败、零忽略；新增正负对照包含在六项内，不与此前单独运行结果累加。保留默认 Info sink 子进程证据：文件首 Warn / 第 60 次 Error、Error stderr、stdout 隔离，以及 owner 替换与抑制断言均通过。未修改生产执行、日志协议、预算、忽略、超时、既有断言或编译配置，没有新增字体资产或依赖。

证据归档 `ui-font-macos-fixture-evidence.zip`：31 个成员、126385 字节，SHA-256 `07dd6894340081d4622d8e6313a0be77eeacc49a039e17fe40a199d0572d3f98`，逐成员读回核验通过；包含原始 macOS 完整任务日志、最终两个测试源、本地输出及四组子进程文件。这里只完成故障夹具修正及相关本地验证，修正后的 macOS、其他平台与整个 UI 套件仍由新头 CI 验证，未据此关闭 #129。
