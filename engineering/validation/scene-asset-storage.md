# 场景图片资产集合复用

对应 #126 第六项，接续 #588，基线 `aef2fd4b483d807abd5ab81dd5ade5b116e49ef0`。
开工核对开放 PR 的文件清单与近期分支；跟踪和原生预渲染由其他分支处理。
本批只处理图片需求收集、活动成员查询与解码许可，不修改那些分支的业务实现。

## 实现与行为边界

`Renderer::prepare_scene_assets` 原先每次构造 `BTreeSet`，活动集合变化时复制，
预取增加候选时再复制一次。现在递归收集到 renderer 持有的 Vec，排序去重，
保持原来的升序处理与去重语义。活动 ID 使用另一份可复用的有序 Vec；预取许可
借用需求切片，仅在栈上保存原上限内的候选，不再复制整个集合。

预取仍先过滤活动 ID，再按原上限取候选；重复候选仍占用名额。需求缺失、全尺寸
和同步准备不允许额外投机结果。取消解码仍同时检查成员、分辨率和解码预算，
没有改变取消标志、busy、结果发布和错误传播。公开的 `scene_assets` 返回类型不变；
其树集合只用于需要独立拥有集合的调用方，不再由逐帧图片准备路径调用。

需求 scratch 在所有 Result 返回后归还，包括预算拒绝、来源失效、解码错误和
`Ok(false)`；它不充当已提交的活动集合。两份 Vec 按本 renderer 观察到的场景
引用数保留容量，在成功替换来源目录和 `clear_assets` 时释放，不延长图片纹理所有权。
新项目校验失败时，仍在修改活动状态前返回，沿用既有非破坏性边界。

## 验证范围

新驻留场景用例先在旧生产实现运行：一张图片、120 次准备就产生 120 次分配，
同一条零分配断言失败。修正后对 1／8／64 张不同图片，分别进行不变需求和
全量／子集交替需求，每种连续调用 120 次，包含实际增加预取候选的路径。
计数只覆盖准备调用的当前线程，GPU 初始化、场景采样、最终绘制和后台线程不计入。
另比较实际捕获的完整 RGBA、纹理台账、解码与上传计数，不声称整帧零分配或 FPS 收益。

有界许可的新用例对 512 组输入、两种启用状态和完整 ID 域比较原树集合实现，
并要求构造与成员查询零分配；另验证重复候选及 0／u64::MAX 边界。
既有三个许可断言保留，旧算法仅作为测试参考，不进入生产构建。

故障与正常等待用例实际执行预算拒绝、未注册资产、移动来源文件造成的原生读取
失败、恢复文件、异步准备与实际解码完成，检查状态／台账与 scratch 归还，最后
验证清理释放容量。现有 LRU、预取、嵌套图片和解码预算断言保持原语义。

最终 22 项不同测试通过：驻留／失败恢复 2、许可 4、LRU 内部回归 3、
图片许可／预取／嵌套工作集／解码预算集成回归 13，0 失败、0 ignored。
启用桌面 FFmpeg 与宿主 diagnostics 的 workspace all-targets 检查通过，
排除已停止维护的 Android，耗时 2 分 22 秒；保留已有未使用项警告。
