## 实际执行的边界

通过正常 `cargo build` 构建 `motion-studio.exe`，没有启用 cfg(test) 的 Engine
构造或注入存储回调。程序以 `--mcp-ui --project ... --locale en` 打开实际窗口，
保留原生事件循环、Shell、Session 和正常缓存目录配置路径。四个独立 PID
分别完成两个 cold/warm 对照，均正常保存和关闭，退出码 0。

每组通过子进程的 `LOCALAPPDATA` 指向独立账户配置目录；两次启动共用该组
目录，工程分别复制，初始工程字节相同。没有修改用户真实缓存、系统驱动缓存
或机器配置。因此 cold 的含义是本应用缓存文件缺失，不代表 OS／驱动全局
缓存被清空；这也没有证明真实默认账户目录的所有现场权限组合。

运行包只把本轮编译的程序和既有 FFmpeg DLL 建立硬链接放在一起，未修改二进制。
程序 120087040 字节，SHA-256
`8e33d6fac073ee0d973fc858ea123fccca1f66c90b3b47f41770c1ed966a456f`。
依赖 DLL 的身份保存在证据包 `runtime-identity.json`，不上传运行二进制。

## 结果及限定

| 场景 | 应用缓存为空 | 下个独立进程恢复缓存 |
| --- | --- | --- |
| 含反相效果的工程：启动到第一次完整画面 | 20406 ms | 19390 ms |
| 无效果工程：启动到第一次完整画面 | 22250 ms | 22094 ms |
| 在无效果工程首次插入反相：编辑回复 | 187 ms | 235 ms |
| 首次插入反相：编辑请求至完整画面 | 500 ms | 485 ms |
| 移除后重加反相：编辑回复 | 62 ms | 63 ms |
| 重加反相：编辑请求至完整画面 | 219 ms | 219 ms |

- cold 状态明确为 `missing`，warm 明确为 `restored`；warm 启动前实际存在由
  上一个进程正常保存的原生缓存文件，不是“内存已有实例”的替代验证。
- 含效果工程两次启动的全部 64×64 RGBA 像素相同，中心为 `[51,204,229,255]`，
  RGBA SHA-256 为 `6b172fe045b7a82fea0db8512bfa6c00db149b59cdc2a8e4d74f79e5b6d22232`。
- 无效果工程两次启动的完整像素一致，中心 `[204,51,26,255]`；两个进程中首次
  添加与重加效果的完整像素也一致，且跨进程一致。逐次 capture 前后原生效果
  管线计数不增长，保证没有用导出捕获偷偷补编译来证明预览准备完成。
- 首次添加后的实际原生效果管线创建数为 4，移除后重加仍为 4，不新增创建。
- 含效果启动实际文件仍为 69397 字节，cold/warm 的内容校验和一致；另一组
  缓存身份与保存时点分别记录，不混用跨组文件。
- 完整帧判据是已呈现 revision 与请求 revision 一致且 preparing=false，
  含效果场景还要求任务 installed；不把第一次 chrome 呈现计为完成。

以上是单组 debug 程序测量，包含正常 Session／UI／字体初始化和 MCP 状态
查询成本，没有隔离背景负载、清空驱动全局缓存或估计统计误差。不能据此断言
缓存显著加速、无前台阻塞或已经达到交互性能目标。20 秒级首次画面的实际成本
仍需按启动阶段继续定位，不能用“最终成功”掩盖启动延迟。

| ID | 分类 | 实际结果 |
| --- | --- | --- |
| 64A-1 | 生产接线验证 | 四个正常应用进程使用真实私有目录验证、Restore/Save worker 与原生窗口，原始状态、日志、缓存身份、退出码可取。已验证 Windows/Vulkan 的这个配置 |
| 64A-2 | 结果与复用 | 全像素 cold/warm、首次／重加比较通过，重加不新增原生效果管线创建，捕获不补编译。已验证该反相效果与格式 |
| 64A-3 | 性能证据 | 保留启动、编辑回复和完整画面耗时；仅一组样本，未建立通用性能结论。后续需要多轮受控对比及启动阶段分析 |
| 64A-4 | 既有错误信道 | 错误帧率 fixture 的程序正常拒绝，原始原因同时在默认文件日志和 Error stderr；MCP 未启动。未修改生产错误处理 |
| 64A-5 | 既有外部错误 | 成功运行仍保留 Epic Vulkan overlay 清单缺失的 loader Error，以及 Windows 内存探测／字体相关 Warn；真实渲染已完成，不隐藏或清空这些记录，也不在本轮宣称修复它们 |
| 64A-6 | 正常协议／窗口边界 | 未发 initialized 通知被 MCP 正常拒绝；隐藏普通窗口后 OS 抑制 redraw，准备结果 ready 但不被呈现轮询收集。改用实际可见窗口验证，不改应用或放宽准备断言；隐藏窗口的正常暂停不算 GPU 准备失败 |

前四次未成功的验收尝试完整保留，分别是：

1. 裸开发程序缺少同目录运行 DLL，后续加载器探针得到 `0xc0000135`，尚未进入
   应用日志；配齐 DLL 后独立 `--help` 探针为 0。
2. 手写 fixture 错把 fps 写成整数，正常应用以 `expected struct WireRate` 拒绝；
   更正为当前 `{numerator:30,denominator:1}`，没有修改工程版本兼容规则。
3. 控制器漏发 MCP `notifications/initialized`，协议以 `-32002` 拒绝；补齐正常
   握手，不修改生产权限或 MCP 校验。
4. 控制器主动隐藏普通窗口，30 秒完整帧断言失败；结果显示 Restore 已 ready、
   preparing=true。保持同一断言与期限，用实际可见窗口重新执行并通过。

每次在原进程确认终止后才修正控制器。没有覆盖旧输出、复用失败目录、放宽已有
测试断言、扩大等待预算、重启产品 worker 或修改产品源码。成功程序的 stdout
逐行作为 MCP JSON-RPC 解析并与请求 ID 匹配；原始文件仍在，错误未混入 stdout。

## 命令、源码与证据身份

`pipeline-normal-app-build`：正常 build 退出 0，154.985 秒。
`pipeline-normal-app-visible-cold-warm`：四个独立应用进程，整体退出 0，93.484 秒。

工程均归档；保留 Windows CRLF 字节，不把 Save 后重排的 JSON 冒充初始字节。

证据包：`normal-desktop-cross-process-cache-evidence.zip`，118 成员，8626587 字节，
SHA-256 `01038e960a90cf7b67c3bfc3f05f0505cf8bd89130133522af6953f853ffe2b0`。
每成员 SHA-256 和 ZIP CRC 已核验。包含实际初始 fixture、stdout、stderr、请求
记录、进程退出码、原生像素、状态、默认日志、诊断、失败控制器和成功控制器。
缓存原生字节不随包分发，仅保留其名称／大小／SHA-256。

本轮没有修改源码或增加 CI job；不改变源码 CI 的 revision，也不把本机证据
替代远端 CI。#64 的嵌套／time-remap 未来范围、可见准备状态、其他格式／精度／
