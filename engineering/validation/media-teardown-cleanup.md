# 音视频任务销毁时的暂存资源清理

## 范围与分支协调

本次推进 #131 第六节的资源释放问题，基于 main `a2bffcf8a4c4f4dd8cf8f4accaa2d88a26a015e7`，使用独立分支 `fix/media-teardown-cleanup`。开始前只读检查了开放 PR 的文件列表、相关本地分支提交及所有 worktree 在目标文件上的未提交改动；没有发现当前任务占用这些文件。不处理其他人的积压 PR、合并、重排、CI 取消或重跑；不修改用户可见 UI。

缓存成对发布已经有备份与回滚；#359 也已经将成功探测结果的暂存资源清理移出任务锁。这些属于既有覆盖，不能重复报告成本次修复。

尚存的两个销毁路径是 `AudioJobs::drop` 与 `VideoJobs::drop`：持有任务锁时直接丢弃 `t.prepared.take()` 的返回值。该值拥有 `Stage`，其析构函数同步执行 `remove_dir_all`，失败时调用宿主日志器。暂存树删除或宿主日志器停顿时，任务互斥锁一直被占用。

## 修改与行为边界

保持同一个任务锁内设置取消标记并取出 `Prepared`；随后显式释放任务锁，再丢弃资源。仍逐个任务清理，仍在当前线程执行，不增加后台线程、超时、重试或重启。没有更改任务状态、元数据、错误、工作线程配额、取消/提交的线性化边界，也不把清理警告转换为导入失败。本次解除的是任务锁占用，不宣称缩短文件删除本身的耗时或让关闭操作立即返回。

这不是新增观察点。`Stage` 的既有 Warn 记录继续包含清理路径与原始 OS 原因；本次只保证上述两个销毁路径调用日志器时不持有任务锁。既有锁中毒观察仍使用原有有界缓冲，在业务锁释放后输出；没有新增计数器或按帧日志。

## 故障证据与验收

新增测试执行实际析构和文件系统操作，不以替代的成功返回值证明清理正确：

- 两个隔离子进程把暂存目录替换为普通文件，使 `remove_dir_all` 实际失败。默认 Info 下的既有 Warn 触发测试宿主日志器，回调使用 `try_lock` 检查取消标记已设置且暂存资源已取出。日志器通过信道保持阻塞期间，另一线程再次检查任务锁；两个检查都必须成功。释放信道之后再等待析构完成，没有基于墙钟帧推进的断言。
- 两个正常路径用实际目录和暂存文件验证删除，保留任务句柄以检查取消标记；同时覆盖没有暂存资源的任务。
- 桌面日志测试通过公开导入接口得到真实 `ready` 任务，再对其暂存路径制造 OS 清理失败。音频使用已有 WAV 素材和实际解码；视频只提供探测结果，实际暂存、缓存写入与析构仍运行生产实现，不宣称完成视频编解码验收。
