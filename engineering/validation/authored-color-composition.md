# 创作颜色工作区合成与原生程序平台验收

## 功能范围

#83 此批增加可直接调用的真实工程颜色路径：
`prepare_native_authored_project` 在已有准备观察范围内，同时保留不可变 GPU
程序集和创作颜色的原生 CPU 程序；`AuthoredSceneSampler` 使用原工程与调用者
提供的 evaluator 采样；`Renderer::draw_authored_scene` 将结果合成到有明确
空间、范围、Alpha 和精度身份的 Float32 工作纹理。显示和输出继续使用已准备的
显式图片变换，不经过中间 CPU 回读。

支持背景、二维纯色层，以及不产生颜色的 Null/Audio 层；支持已有二维变换、
层不透明度和小数帧采样。当前要求工作空间声明为 scene-linear、scene-referred、
完整范围、预乘 Alpha，工程与实际目标均为 Float32。这只是明确的消费者切片，
不是普通 Session 已具备完整工程色彩管理的声明。

创作颜色按输入 Alpha 反预乘，归一化有限 RGB 码值范围，再执行准备时保留的
原生 OCIO CPU 程序。采样结果保持直通工作 RGB，由实际绘制或背景清除预乘一次。
既有 sRGB 解码只用于旧路径；已经转换的工作颜色不会再次解码，也不会为了
进入旧渲染器而重新编码为 sRGB。原生输出的负值和高于一的 RGB 不裁剪。

帧内部 Scene 不公开，避免误交给旧消费者。两个可复用 Scene 只有在整帧采样及
变换全部成功后才交换发布。evaluator 每帧调用一次，其结果在 Scene 解析前
再次核对颜色声明及消费者资格。失败保留上一已发布帧，但返回 Err，调用者
仍必须转送错误，不能将 `current()` 用作隐式成功回复。

未接入的效果、矢量、蒙版、遮罩、嵌套合成、素材及三维消费者明确拒绝，不走
旧颜色转换。目标所有权、完整颜色身份和尺寸在写入前检查；提交保留目标纹理
资源账本，并沿用驻留来源及分配预算检查。原生程序留在创建线程，没有新增
`unsafe Send`、后台重启、超时或运行时重试。

## CI 原生程序比较的授权修订

远端 `3f5e4708` 的 run `42453532175`：Windows/Linux/macOS Intel 桌面测试、
Rust/GPU、审计及 Windows 原生构建通过；Linux/macOS 原生构建成功，但原生
数值资格在第 8 组的程序 JSON 全等断言失败。没有将该 run 记为绿色发布。

解析完整原始失败记录得到：配置、选择、版本、阶段和 Alpha 身份完全相同。
Linux 的着色器非数字结构一致，735 个数字中 25 个不同；第二张表有 68 个
不同值，最大绝对差 `0.0000762939453125`。macOS 着色器字节相同，第二张表
有 29 个不同值，最大绝对差 `0.000049591064453125`。这些是生成结果的差异
事实，不据此断言某个系统数学库是根因。

从两份真实 CI 输出还原程序，在本机 Windows Vulkan 上分别执行第 8 组全部
12 个像素，均符合未修改的 CPU 参考与容差。这不是两平台自身 GPU 的验收。
随后准备具体修订草案及 9 项变异负对照，用户明确授权“允许修订并保留严格负对照”。

修订只调整原生程序资格的比较范围：身份、版本、阶段、Alpha、表结构、整数、
标识符、运算符、注释、布局和非浮点文本继续精确比较；浮点字面值与表数值
须有限，并采用原有绝对/相对数值容差。没有修改程序生成器、参考文件或像素
容差。错误身份、Alpha、表宽、表数值、NaN、表达式、浮点常量、绑定整数和
表长度九个负对照必须被拒绝。

CI 同时增加每个平台**本次实际生成程序**的 GPU 图片验证：20 组、240 个像素
对比原 CPU 参考，Alpha 位完全相同；另实际执行错误着色器和错误表的 GPU
负对照。原生准备、创作合成及默认错误信道均为必须通过的步骤，没有
`continue-on-error`，CI 不生成新参考值。

## 本地实际证据

本机 Windows x86_64、Vulkan，复用已逐项验证的固定原生核心及重新构建的
当前初始化桥接库，没有把它记作本次完整第三方源码重建。

| 项目 | 结果与实际边界 |
| --- | --- |
| 真实创作颜色 | 三份配置、直通/预乘输入，48 个工作区色块及各自显示/输出端点符合既有 CPU 链参考；工程 JSON 不变 |
| 有限范围 | 162 次色块检查，包含零 Alpha；配置文件在准备后删除，两个备用 Scene 仍连续采样三个小数帧，不发生隐藏的配置重读 |
| 负值/HDR | 用二进制精确有限码值区间保存合法的 `[0,1]` 工程原值，解码原参考的负值/HDR 输入；72 个色块符合原 CPU 容差，实际读到 18 个负值和 54 个高于一的通道 |
| 合成与拒绝 | 小数帧不透明度和半透明背景的实际 over 像素正确；两个实际错误 GPU 管线被检出；错误目标颜色身份/尺寸不写目标；陈旧声明、三维消费者及非有限时间拒绝，不发布新帧 |
| 原生数值 | 原生资格 6 项通过，含 20 组/240 个 CPU 样本、初始化异常、资源/环境拒绝和九项结构/数值负对照；实际生成程序 GPU 验证及两个错误 GPU 程序通过 |
| 既有路径 | 图片处理器 14 项、原工程准备/文件输入 9 项、宿主准备/容量 3 项通过；这些结果不代替全产品渲染验收 |
| 默认信道 | 六项桌面颜色日志测试及媒体清理日志回归通过；真实不支持消费者保留 request、目标、阶段、对象及原因，文件 Error/stderr 一致、stdout 隔离、工程不变、in-flight 清除；另有四项实际捕获日志负对照 |
| 工具 | 标准发现 144 项，143 通过、一项原有可选跳过；70 项工具库存和 6,371 个跟踪路径的来源门禁通过 |

首轮新测试误用私有 `motion_core::expressions` 模块的编译失败保留；最终使用
已有公开 evaluator 导出。没有为通过测试改变现有断言，除本节和原日志文档
明确记录的用户授权修订。两条原日志修订的生产 logger 未改动。
