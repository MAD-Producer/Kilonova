# 原生 OCIO 初始化异常边界验收

## 问题和修正

#83 的原生桥接原先把初始化声明为 `noexcept`，却直接调用可能抛出异常的
`SetLoggingFunction`。实际异常会终止进程，无法进入宿主已有错误信道。
本批把初始化接到已有 C ABI 分类边界，返回有界原始原因；只有版本、回调和
原生注册全部成功后，才发布 Rust 回调。所有导出在注册前解析，失败不安装
进程级运行时。固定 OCIO 源码的 setter 在互斥锁内完成回调赋值，没有赋值后
的可抛出操作；此结论只适用于已固定的 2.6.0 源码。

初始化 ABI 随之变更。已有桥接源码 SHA-256 门禁会在动态加载前拒绝旧桥接，
没有兼容垫片。库加载与导出解析错误另增加操作、库路径，保留原始
`libloading::Error` 作为 source；不是将系统错误替换为一般字符串。

## 实际验证

- 独立编写的 C++ 验收单元直接编译生产 `bridge.cpp`，只在该验收翻译单元
  置换版本查询或回调注册。依次触发版本错误、真实 OCIO 异常、真实
  `std::bad_alloc`、标准异常、未知异常及 8 KiB 原因。分类分别为
  1/2/3/4/5/4；原因保留，长原因限制为 2047 字节并以 NUL 终止，失败均未
  发布回调。空回调在注册前拒绝，随后正常注册成功并清除上次错误。
- Rust 准入单元 4 项通过，包含实际加载非动态库字节、实际查找不存在的
  导出。两条真实系统错误保留操作、路径与原始 source。
- 原生集成 5 项通过。新增受控子进程加载单独构建的故障 DLL，通过实际
  生产初始化函数取得 category=3 和原始原因；随后显式加载正常运行时并
  执行真实 ACES CPU 处理器。此步骤证明失败未安装无效运行时、未污染初始化
  锁；它是测试中的显式调用，不是生产自动重试。
- 既有 20 组处理器、240 个 CPU RGB 样本及着色器/表/配置身份检查继续通过。
  宿主原生工程准备 3 项通过；未重生参考或放宽容差。
- 桌面默认日志 5 项通过。新增真实 `bad_alloc` 从 provider 到宿主默认
  logger，文件和 stderr 各一条 Error，包含 request=8301、DefaultInput、
  initialize、category=3、elapsed 和实际 `bad allocation` 原因；Info 开始
  先于失败，stdout 隔离，工程 JSON 不变，在途状态清除。四个实际捕获输出
  负对照分别移除文件 Error、清空 stderr、丢失原始原因、污染 stdout，均拒绝。
- 工具完整检查 135 项：134 通过，一项原有可选检查跳过。留存证据时调整
  CI 的输出目录后，配方/打包/工作流定向 27 项再次通过。一次定向调用忘记
  已固定的 PyYAML 工具路径而导入失败，保留输出；沿用原工具路径后通过，
  没有改断言或新增依赖。

Windows 本次只重建自有桥接和验收目标，复用此前完整构建并逐文件验过
身份的未变 OCIO 核心、头文件和导入库。不是再次完整编译第三方组件。
最终正常前缀只有核心和正常桥接两份运行库；故障 DLL 与验收程序留在 build
目录，无安装规则。故障前缀仅由 Rust 测试构建，带 `qualificationOnly`
标记，打包器实际拒绝该标记。发布清单必须在 C++ 边界验收通过后才能写出；
缺验收的发布负例通过。CI 复用这些步骤，并在失败或非 PR 场景留存原生过程
及默认日志证据，不改变成功 PR 不上传构建产物的规则。
