# 按图层时间映射预取视频帧

## 问题与改动

既有预取始终选择当前素材 PTS 后面的四帧，缓存也只保留正向窗口。倒放时提前解码的低 PTS 会在后续请求中被丢弃；往返重映射和冻结则会预取不再需要的帧。

对包含时间映射的当前视频实例，改为预测接下来四个合成帧，经图层时钟、片段边界、嵌套帧率和 source-start 得到素材时间，最后才查实际 PTS 索引。按实例身份区分同一子合成的多次引用，重复时间和冻结去重；Linear 混帧的当前左右帧仍优先、固定保留。

缓存只保留当前必需帧和计划内目标。解码检查与回填也使用同一目标集合，过期的推测解码正常取消。原有最多四个解码线程、每实例最多五个缓存帧和字节预算不变。没有时间映射的片段继续采用原有正向策略；精确采样／导出入口不启用此预测。

预取规划失败只关闭该次推测工作，当前必需帧仍按原路径请求、返回或报错；没有清除必需帧的错误、重启线程或增加重试。新观测与这项功能边界分开说明如下。

## 验证

最终宿主 `video_` 分组 46 项通过，包括七项新规划／真实 worker 用例、现有 VFR 混帧、缓存预算、资源回收、受控解码阻塞与失败回归。新用例验证倒放后续缓存跨请求保留、往返目标去重、当前混帧对固定保留、冻结、片段右开边界、不同帧率的嵌套双倒放与 source-start、重复实例，以及取消、推测失败不污染必需帧和原始模型原因。

桌面带 FFmpeg 的两项新用例通过。实际 CFR 与 VFR 文件分别覆盖二倍速、倒放、冻结和往返重映射，每组合八个采样点，共 64 点；使用独立公式核对素材时间、独立 FFmpeg 解码器核对 PTS 与全部 RGBA 像素，并核对缓存上限。冻结只解码一帧，完整工程内容保持不变。

默认错误信道用例先通过真实 FFmpeg 准备当前帧，再注入工程缺少场景对象的规划故障：120 次失败仅在第 60 次记录一条 Error；成功一次后，再失败 60 次产生第二条。180 次故障调用仍返回原当前帧。实际应用 logger 的文件与 stderr 各有两条原始原因记录，stdout 不含这些日志。

带 FFmpeg 与 diagnostics 的 workspace all-targets 检查通过（排除已停止维护的 Android 包）。原始输出、源码与二进制哈希、原生统计报告见[清单](mapped-video-prefetch-evidence/manifest.json)和[证据包](mapped-video-prefetch-evidence/evidence.zip)。PR CI 在提交时尚待运行，不以本地检查代替 CI 结果。

## 首轮记录、集成与限制

首次宿主编译遇到新测试对非 Debug 的成功类型使用 unwrap_err；夹具改为取 Err，不给生产帧类型添加无关实现。首次原生像素测试的基础夹具过长，被既有“video clip exceeds recoverable source interval” 拒绝；将新夹具改为覆盖全部八个既定采样点的合法半秒合成，保留原模型校验、采样点和像素断言。首次错误信道用例已经通过，随后按最终源码重新通过。首轮输出保留，没有修改既有断言或生产预算。

基于已合并的 #579（main `9d085c0f`），其树与原已验收分支头一致。基准的全部必需 CI 通过；Linux 日志显示清理预装 SDK 后可用空间由 85G 变为 102G，该 runner 完整构建通过。这不构成本分支的新 CI 结果。

本修复只预测当前已采样视频实例，尚未提前创建未进入片段范围的解码实例。没有把这项修复称为所有首次显示卡顿的解决方案；预热新图层／pipeline、连续锚点补偿、高速音频质量与最终集成仍有后续工作，#257 保持打开。
