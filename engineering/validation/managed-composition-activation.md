# 受管颜色工程的合成切换

本批继续 #83，修复打开合成时仍先创建旧版 Scene，导致受管工程无法切换的缺口。
目标合成先独立准备原生采样器、采样目标时间并准备窗口源绑定；全部成功后才
提交活动合成及其上下文。失败不先改工程、时钟、选择、观察摄像机或已发布画面，
不靠切回旧合成、重试或清除错误恢复。未受管工程保持原有采样与错误语义。

| 编号 | 分类与处置 | 证据及限制 |
| --- | --- | --- |
| MCA-01 | 功能修复 | 受管合成不再进入旧 SDR Scene 构造；先准备完整目标候选，再调用活动合成提交。候选仅采样一次，成功安装后不重复求值 |
| MCA-02 | 独占原生所有权 | 新采样器通过已验证的库所有者创建独立 native program；不克隆或共享原生处理器句柄。已验证配置字节与不可变 GPU 程序按原身份共享，不重新打开配置或运行时清单 |
| MCA-03 | 窗口源准备 | 相同显示程序不等于相同图片源。目标引用的静态源集合变化时，在提交前准备完整 working images；素材缺失及真实预算拒绝保留原合成与旧前台 |
| MCA-04 | 原生宿主资格 | 不同尺寸、帧率、长度的合成往返，核对原 CPU 颜色、目标帧钳位与保存、选择过滤、时间轴上下文、同合成重开和历史/工程 generation 不变。准备后移除配置文件；不支持的目标、表达式错误及不存在目标均拒绝且原状态严格不变 |
| MCA-05 | 实际 GPU 窗口 | 六组输入、16-bit 原始图片、单/双/四视图，双向切换各比较常色内部，107520 个 surface 像素使用独立原生 CPU 参考及既有一个码值容差。错误保留旧源的对照颜色必须可见不同；缺源一次及预算拒绝两次后显式恢复 |
| MCA-06 | 新日志覆盖 | `prepare_color_composition` 沿已有观察器发布 start/in-flight、完成耗时及原始失败，包含目标合成。表达式失败保留目标与采样阶段。真实 worker 验证失败不改变工程、时钟、历史、合成上下文、显示 revision 及 renderError，随后可显式成功切换 |
| MCA-07 | 命令原因链修复 | 首轮真实 worker 暴露 CompositionContext 包装使请求级日志缺少底层颜色拒绝。现有有界原因格式器识别最多八层已知 Context/CompositionContext；原协议及返回值不变。要求该原始原因同时出现在准备日志和真实请求编号的 Error 记录，未改成只要求任意一处出现 |
| MCA-08 | 默认信道与既有覆盖 | 实际默认 Info 文件记录 start，Error 同时进入文件及 stderr，stdout 隔离；解析真实请求耗时，要求 start 先于失败。既有受控阻塞、panic/清理、锁重入及观察容量测试继续回归；本批没有增加超时、重启、自动重试或 Present 日志 |
| MCA-09 | 正常分支与边界 | 合成切换不创建编辑历史；相同活动合成使用实时帧，其他合成恢复各自帧。观察摄像机重置沿用既有行为；不支持的颜色消费者仍明确拒绝，不使用未受管 Scene 冒充受管数据 |
| MCA-10 | CI 与来源 | 新宿主测试纳入既有 authored 原生门禁，worker 错误测试在打包前强制执行，工具检查命令不可缺失。无依赖、资产、面板、布局及样式令牌变化；DESIGN §0.7 项均保留，本批不涉及其整改。原 CPU golden、容差和原生运行时身份不变 |
| MCA-11 | 未完成范围 | #83 仍有取色/录制、其他输出、附着精度/显示事务、视频/效果/嵌套/三维消费者、ACES 2 及跨平台/OS 显示资格。本批只补合成激活，不能据此关闭该 issue；只继续此 issue，完成后按用户要求停止 |

证据目录：`artifacts/issue-goal-current/color-managed-compositions/`。
新测试首轮编译时误序列化非序列化的颜色契约，改为在状态元组中直接比较契约；
下一轮图片 IO 变体的夹具匹配写错，修正为原有类型；新合成 ID 首版漏了模型
要求的 `comp-` 前缀。这些错误输出分别保留于 first、second 和 third。

第四轮的新宿主颜色期望误把 Scene 的直通道 tint 当成已预乘工作纹理，改为直接
比较原 CPU RGBA；实际 GPU 仍按既有预乘一次的像素语义验证。该轮新图片错误
检查又未考虑现有 Box 错误包装，现严格逐层匹配 SurfaceDisplay、SourceImage
及原生 NotFound 类型，而非删除检查。第五轮宿主及真实窗口通过。

`worker-first.txt` 与 `worker-first-channels/` 保留实际请求级原因缺失的生产失败。
未缩减“双处原原因”断言，修复日志包装识别后重跑。历史子窗口的原始 stdout/
stderr 未在每轮另存独立副本；第三、第四轮父输出包含当时子失败，不能宣称
拥有这些轮次的单独原始子信道文件。

DX12 首轮窗口子进程发生 `0xc0000005`，保留 `composition-dx12-first.txt`、
`dx12-first-channels/` 及 Windows Application Error 事件；不能将其计作通过。
新增测试阶段和实际后端输出后，一次诊断调用完成全部 107520 个像素，见
`composition-dx12-diagnostic.txt` 与 `dx12-diagnostic-channels/`。没有对应的
生产修复，后一次通过不能证明已修复首轮崩溃；DX12 稳定性仍待根因定位。
未给生产代码加重试，也没有修改断言或自动绕过失败。旧原生批次曾有访问冲突，
但本批没有证据认定两者同源。Windows 事件中的旧二进制已被后续编译替换，
没有保留其独立可执行文件及 PDB，不能用新版符号冒充旧崩溃栈。

后续 `composition-vulkan-final.txt` 也失败：headless 一项通过，但窗口子进程
访问冲突，stderr 带有栈溢出提示，最后输出处于 config=1、Premultiplied、
单视图切换。因此不能归因为 DX12，也不能将该次调用算作两项通过。

从机器既有 WER DumpFolder 找到两次转储，复制到 `wer-original/`，同时保存
Vulkan 对应可执行文件和 PDB。Vulkan 转储模块的 RSDS GUID/age 与保存的
可执行文件相同；DX12 旧文件仍缺失，保留其原先的符号限制。Vulkan 线程栈
中找到 405 组异常记录/上下文，最早可识别记录为 WGSL 字符搜索路径的读取
访问冲突，读取地址为 `0x62df`；后续记录在系统异常分发中重复。它给出的是
定位线索，尚未证明调用方、原生桥、编译器或资源生命周期中的哪一处是根因。
恢复出的局部栈在更高帧处无法可靠展开，不能冒充完整、可靠的原始调用栈。

独立外部调试器的第二次 Vulkan/DX12 调用分别完成全部 107520 个像素，
未捕获访问冲突。临时进程内 first-exception 捕获器的两种后端调用也通过，
没有产生异常转储；它保持异常继续分发，未加入恢复、重试或替代结果。
该临时代码已经从测试源移除，相关 DLL、诊断源码与可执行文件只保存在
证据目录。临时构建调用的筛选器未匹配测试，输出为 0 项，它仅证明编译，
不计入通过数；四次诊断通过均不能代替对两次崩溃的生产修复。

完整首轮矩阵有 49 项不同 Rust 测试、1 项所有权 compile-fail 文档测试及
29 项工具测试通过；默认 Info 的真实 worker 验证三条 Error 同时进入文件
和 stderr、stdout 隔离。其后的 GPU 崩溃意味着本批稳定性资格仍未完成。
四份既有 CPU golden 的字节身份及原容差未改变。

Vulkan 与 DX12 稳定性仍待验证，也不能用它们代替 Metal 或其他平台真实窗口
资格。冻结显示快照等此前批次的证据保持原样，不能用旧提交 CI 结果替代
本提交的必需检查。本批提交只供审阅和 CI，PR 保持草稿，不关闭 #83。
