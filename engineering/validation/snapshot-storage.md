# 同帧输入快照与直接绘制的临时列表

接续 #589 的场景图片集合复用，仍处理 #126。基线为
`4bd7cd18a173458a3a385aaab1323f10e85e5122`；开工重新核对开放 PR 与近期分支，
没有修改其他 agent 正在推进的跟踪／预渲染业务。

## 本阶段改动

`encode_effects` 不再复制已经存在的当前帧快照顺序；准备和编码阶段都借用
同一个已验证的执行顺序。失败程序引起的既有预览重建仍在原循环内进行，
成功构建之后才继续下游，不增加重试或改变原来的拒绝／旁路策略。

`prepare_input_snapshots` 不再收集一份 specs Vec 和一份 stale Vec，改为
读取当前计划的尺寸、格式与来源，直接在图片表内移除失效快照。清理时仍逐项
扣减记账、失效绑定；计算需求、LRU 裁剪、旧目标的峰值准入与替换顺序保持不变。
图片缓存裁剪和 GPU 准备只失效资源绑定，不重建当前帧计划，因此这些读取使用
相同的来源／顺序／尺寸。没有把临时列表转移成新的长期纹理缓存。

直接绘制分支也在原图片表内清理遮罩及输入快照，移除成功后沿用原来的
mask pool 清理和一次绑定失效。原来的空 Vec 本身不分配堆内存；这里消除的是
从效果／遮罩切换为直接绘制时的过期 key 列表，不宣称修复空场景的逐帧分配。

## 实测及失败路径

新快照用例先在基线执行：已驻留的一个来源，连续准备 120 次实际产生 120 次
分配，同一条零分配断言失败。修正后，1／8／64 个链式依赖来源各 120 次准备
均零分配；准备前后的完整纹理台账、记账、已完成像素及再次绘制结果一致。
计数只覆盖准备调用线程，不包含计划构建、GPU 初始化、最终编码和后台线程，
不能据此声明完整预览帧零分配或 FPS 收益。

另一真实 GPU 用例生成遮罩与八个输入快照，移除一个依赖后只清理过期项，
其余快照、遮罩、额外静态图片和既有输出继续有效。转为直接绘制后核对遮罩／
快照清理、静态纹理身份与实际总字节，重复空清理不分配；最终完整像素与新建
renderer 的直接绘制结果相同。

原有 `input_snapshot_refusals_retain_layer_extent_typed_causes_old_texture_and_pixels`
完整执行，验证总准入和来源分类预算两种真实拒绝、原始类型／上下文、旧纹理、
旧输出以及恢复。私有准备入口改为读取当前计划，所以既有夹具先新增断言，
要求该顺序与原先独立计算的顺序相等，再调用入口；原有拒绝与像素断言没有修改。
首轮编译因这个旧调用仍传入参数而失败，原始日志保留，不把编译错误称为功能负对照。

本阶段最终执行结果见[清单](snapshot-storage-evidence/manifest.json)及
[原始证据](snapshot-storage-evidence/evidence.zip)。场景图片集合上一阶段的
22 项证据继续保留；不能将两个阶段的重复用例累计成新的不同测试数。

当前最终源码执行 21 项不同测试：snapshot 过滤的 9 项、图像导入／输入顺序／
原生共享快照集成回归 10 项，以及场景图片存储回归 2 项，0 失败、0 ignored。
真实 GPU 共享来源覆盖四种精度及不同堆叠顺序，资源导入覆盖曲线／遮罩与纹理身份。
带 FFmpeg／diagnostics 的 workspace all-targets 检查通过，排除 Android，
耗时 1 分 47 秒；保留已有警告。
