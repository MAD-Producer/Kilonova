# 遮罩规划复用与整帧分配实测

基于 `9a2ae9f09136107038387fd4417115b867da80d4`，接续 #589，推进 #126。
实施前核对开放 PR 的文件列表和最近分支，避开其他 agent 的跟踪与预渲染实现。

## 实现

Renderer 保留当前遮罩纹理需求、依赖遍历的 active／done 集合和输出顺序，
每次清空内容后复用容量。遍历保留原 DFS 的顺序、alpha／luma 双重身份、
去重和循环拒绝；编码读取本次准备结果，不跨场景缓存拓扑。
需求列表保留原顺序和重复项，不以排序改变资源创建及错误归属顺序。

CompositingGpu 复用预算计算中的唯一目标集合；仍先检查完整预算、在临时表
准备所有新增目标，再发布替换。失败不改变旧纹理、绑定、尺寸或记账。
release 清空集合；容量随现有 matte 表保留。生产帧受 MAX_LAYERS=128 限制，
这些集合仅保存当前需求与遍历，不积累历史帧。clear_assets 释放 Renderer
的规划容量。没有增大纹理、任务或错误观察预算。

## 先失败再验证

旧生产实现上，120 次八层依赖遍历产生 600 次分配，一组目标重复准入产生
120 次分配；新增的零分配断言均实际失败。改动后，1／8／128 层遍历及
1／8／128 来源、包含重复与双模式请求的目标准入，各 120 次均为零分配。
独立保留旧 DFS 为顺序参考，512 组变化图、循环错误及随后健康恢复均比较
完整结果。断言未放宽；遍历测试仅为新的容量所有者调整调用入口。

真实 GPU 测试核对完整资源台账、纹理身份及记账。既有五项遮罩准入验收
覆盖实际分配拒绝、来源分类预算、旧绑定和完整像素保留、命令放弃／完成
后的释放与恢复。图层合成和四种精度的原有集成断言保持不变。

最终 22 项不同测试通过：规划 4、完整预览测量 1、既有遮罩准入 5、图层合成
7、精度集成 5，0 失败、0 ignored。带 FFmpeg／diagnostics 的 workspace
all-targets 检查通过，排除 Android，耗时 1 分 52 秒；已有警告保留。

## 完整预览帧测量的结论

每种场景运行 20 帧，前四帧暖机，后 16 帧分别记录采样、资产准备、encoder
创建、encode_preview、finish／submit 和设备完成查询的成功分配次数。
每帧改变所有图层的实际变换，测量后读取像素，确认画面发生变化，并逐字节
比较最后一帧与新 Renderer 的正式 capture 输出。遮罩使用每组最多八层的
链，遵守现有深度限制。截图读回和参考渲染不计入预览分配。

本机每组 16 帧计数均相同。以下为**调用测试线程的成功分配次数**，包含 Rust
原生后端调用，非分配字节、耗时或 FPS；不覆盖其他线程及驱动外部分配。

| 场景 | 图层数 | 旧整帧计数 | 新整帧计数 |
|---|---:|---:|---:|
| 实色 | 1／8／32 | 66／71／77 | 66／71／77 |
| 矢量 | 1／8／32 | 120／255／698 | 120／255／698 |
| 遮罩 | 1／8／32 | 66／834／3127 | 66／826／3113 |

这次只移除了规划临时容器，不能消除编码与提交的所有分配。数据直接表明
#126 的整帧验收仍未完成；不能用局部零分配、通过数或显存台账代替它。
后续需定位矢量和遮罩编码／提交中的增长项，并扩展到实际桌面呈现、分配
字节、其他后端及更多工作负载。本记录不设置依赖驱动的固定总计数门禁。
