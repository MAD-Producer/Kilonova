# #83 原生运行时随包交付与平台门禁

在 `native-ocio-preparation.md` 的准备接口之后，本批把固定原生 OCIO 接入
桌面构建和发包路线。普通 managed Session 的渲染接线仍未完成。

## 实现

- Apple ARM 显式使用 OCIO 2.6.0 上游选择的 sse2neon 提交
  `227cc413fb2d50b2a10073087be96b59d5364aea`；原始归档 136,342 字节，
  SHA-256 `3427a495743bb6fd1b5f9f806b80f57d67b1ac7ccf39a5f44aedd487fd7e6da1`。
  CMake 使用显式 include 目录，不触发该依赖的隐式下载。不改上游头文件。
- Windows/Linux/macOS Intel 使用原七个组件；Apple ARM 再加入这个头文件和
  第八份许可证。Rust 根据平台核对完整组件集合和每一份原始许可证。
- 打包器显式接收 `--ocio-runtime`；核对源码/桥接身份、架构、库集合、
  哈希、相对路径及原始许可证，再保留运行时目录结构。
  Windows/Linux 放在 `native/ocio`，macOS 放在应用 Resources/ocio。
- macOS 先签署实际 dylib，再写入签后库哈希，最后签应用。原始构建清单
  单独保留为 `OCIO-SOURCE.json`，不因签名改写构建前缀或源码收据。
- 发布汇集器重新检查归档中的清单、源收据和逐文件清单，缺库拒绝发布。
  `ocioNative` 只表示包中有该运行时，不声明整个应用已支持 managed 色彩。
- 原生桌面矩阵在 PR 也执行真实 OCIO 构建、CPU/GPU 程序参考和工程准备，
  不重新生成参考。发布包显式接收该次通过资格的运行时。Windows 仅导出
  MSVC 构建所需环境，不打印环境全集。失败保留日志和 in-flight 记录。

## 实际证据和限制

- Python 完整工具检查：134 项，133 通过，一项原有可选检查跳过。
  四平台归档测试使用合成架构头和真实原始许可证；macOS 签名操作以实际
  改变夹具字节模拟，不能当作 macOS codesign 运行通过。
- 八份离线许可证与固定提交 SHA-256 完全一致；Git 对这些文件禁用换行转换。
  缺许可证、错误源码/桥接、平台、路径、重复项、缺库和损坏字节均实际拒绝。
- 真实 Windows OCIO 库经过打包、解包后，4 项原生集成测试通过，包括
  20 组处理器、240 个 CPU 样本，GPU 程序及数值表沿用原有完全相等检查。
  Rust 准入 2 项通过；工程准备 3 项通过，包含三份真实配置、工程不变与容量拒绝。
- 这份 Windows 归档中的 shell/FFmpeg 是明确标注的合成夹具，OCIO 库和
  许可证是真实构建产物。没有把该归档当作产品发行版执行验收。
  首轮先逐文件验证复用未变化的 Windows 核心和桥接，再用当前配方从七份
  固定归档完整重建所有 Windows 组件和桥接库；新产物再次经过打包、解包，
  原生 4 项、工程准备 3 项均通过。两个批次、各自清单和脚本分别保留。
  完整重建首轮在 MSVC 编译器自检时报 D8050，未发布清单；改用此前编译
  验收相同的显式 TEMP/TMP 后，新目录的完整构建通过。原始失败未覆盖，
  不把环境对齐宣称为已定位 MSVC 内部根因。
- 首轮完整工具检查因新证据上传步骤与已有 PR 成功时不上传构建产物的规则
  冲突失败。修正工作流为失败时或非 PR 时上传，保留原始失败，未改已有断言。
